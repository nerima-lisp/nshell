# L02: Git prompt responsiveness in a large repository

1. Prepare a disposable Git checkout containing at least 20,000 tracked files, with the prompt configured to show branch and dirty status. Run on an idle Apple Silicon macOS host and an idle CI Linux host; keep the checkout, build, and terminal settings fixed for each host. `NSHELL_PROMPT` replaces the prompt format, so set it in the launcher environment to a unique format such as `L02_PROMPT_<run-id> {path}{git} `, retaining `{git}` so branch and dirty status remain visible.
2. Put a fake `git` first on `PATH`, outside the checkout. It answers `symbolic-ref` with a branch name at once, and for `status` it logs a start line, sleeps 3 seconds, and logs an end line. Start a fresh shell and use a PTY harness with a monotonic clock to measure the time from process creation to the prompt marker. Do not type the prompt marker into the shell.
3. In the same session, confirm from the log that a `status` call has started. Type and run `echo L02_READY`, and confirm that the command output appears before the log shows any `status` call ending. Exit the shell; it may wait for the sleeping `status` call before it exits.
4. Repeat steps 2 and 3 in five fresh sessions.
5. With the real `git`, confirm branch information appears when available. For the record, collect five fresh-process warmups and then 30 fresh-process measurements of startup and of empty Enter (from sending Enter to the next prompt marker), and repeat the complete run once. Report the two medians and the sample range for each measurement, together with the repository fixture, platform, build, and sample counts.

Pass when, in every session of steps 2 to 4, the prompt appears within 2,000 ms while `status` sleeps, a `status` call was observed, the command output appears before any `status` call ends, and the shell exits cleanly. This checks that Git status work does not block the prompt or input: a shell that waited for `status` would take at least 3,000 ms to show the prompt however loaded the host is, while a shell that does not wait only starts later under load. The 2,000 ms bound stays 1,000 ms below that floor and well above the largest startup seen on shared macOS CI runners (327 ms). The startup and empty-Enter numbers of step 5 are recorded only and do not decide the result; the 150 ms and 60 ms targets are reported next to them. Performance is guarded by later relative checks on a local machine against the v0.7.0 baseline (task P0-7 in `docs/design/tasks/P0-foundation.md`).
